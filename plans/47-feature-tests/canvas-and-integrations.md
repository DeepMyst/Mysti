# Canvas, visual workflows, and external integrations

Source-inspected on 2026-10-09. This is an inventory and execution plan, **not a test result**. No live providers, accounts, channels, or long-session campaigns were exercised for this document. Registration and call-site tracing establish reachability; existing test files establish available coverage, not that the current product passes a scenario.

Use the shared fixtures, evidence format, and profiles in [the main plan](../47-comprehensive-feature-test-plan.md): **S** = 45–60 minutes / 25 meaningful turns or operations; **W** = 8 hours / 250 turns; **E** = 24 hours / 750 turns or operations; **P** = five days / 1,000 turns with nightly shutdown. A feature's action count below is embedded in that profile, not an instruction to repeat every feature 250 times. Keep real development work between targeted actions, retain the same evolving project and conversation, and include both human edits and agent work. Record actual elapsed time and completed turns; an accelerated timer test is supplemental evidence only.

Fixtures used here: **F2** full-stack app, **F3** large monorepo, **F4** untrusted content and synthetic secrets, **F5** Canvas app, **F6** two isolated service accounts, workspaces, and peers. Give F5 a realistic developer-tool design brief: a task dashboard, task detail, settings, mobile view, and release landing page, with distinct copy and acceptance criteria. Keep all external sends and mutations in explicitly designated test accounts/recipients. Use disposable CLI configuration homes and plugin repositories. Capture a baseline of files, processes, connections, and permissions before each campaign.

**Status vocabulary:** *Wired* means a contributed command/current UI has a production handler; *Conditional* adds a dependency or opt-in; *Partial* means only the named subset is wired; *Library only* means supporting implementation lacks a current production route; *Absent* means no implementation/entrypoint was found for the requested behavior. A negative reachability check can pass as a security check, but **does not make a visible broken affordance or advertised unavailable feature acceptable**. Such cases require either working behavior or an accurate disabled/unavailable surface before product acceptance.

P0 = data loss, isolation, security, or core daily reliability; P1 = important usable workflow; P2 = conditional enhancement or future acceptance. Save sanitized transcripts, screenshots, request/operation receipts, persisted artifact/file hashes, process inventories, and error/permission events under each case ID. Never capture real tokens. For visual results, compare semantic content, DOM/layout measurements, and screenshots; an agent's claim that a page looks right is not an oracle.
