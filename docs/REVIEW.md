Mysti is a TypeScript VS Code extension that combines a common interface for 15 AI backends with its own model-driven coordinator, several collaboration workflows, an editable design canvas, context and memory management, and DeepMyst account/tool integration. The current application is substantially larger than the README's older release descriptions suggest: 220 source files, approximately 130,000 source lines, 183 configuration properties, and 30 contributed commands. Those figures describe this checkout, not a verified Marketplace release.

The principal architecture and execution paths are:

| Area | Main files | Actual responsibility |
| --- | --- | --- |
| Activation | `src/extension.ts` | Constructs managers, injects dependencies, registers commands and webviews, starts provider discovery and account initialization in the background. |
| Chat | `src/providers/ChatViewProvider.ts`, `media/chat/` | Owns panel state, message routing, context assembly, stream handling, questions, permissions, setup, and integration with the other subsystems. |
| Provider infrastructure | `src/managers/ProviderManager.ts`, `src/providers/ProviderRegistry.ts`, `src/providers/base/` | Registry, capability metadata, model resolution, prompt construction, process/session management and normalized stream events. |
| Coordinator | `CoordinatorModelClient`, `_runMystiAgentic`, `coordinatorTools`, `MystiTagScanner` | Runs Mysti's own LLM and dispatches tools or delegates work through a bounded loop. |
| Collaboration | `BrainstormManager`, `MentionRouter`, `CollaborationManager`, `SessionManager`, `MystiOrchestratorManager`, `CollaboratorPool` | Distinct interaction shapes, task routing, and dependency-aware execution. |
| Canvas | `src/canvas/`, `CanvasManager`, `CanvasOpExecutor`, `ArtifactStore`, `src/webview/canvas/` | Persistent document editing, agent/human operations, history, live previews and host/webview synchronization. |
| External tools | `DeepMystAuthManager`, `DeepMystClient`, `ConnectionsPanelManager`, `McpClient`, `McpConfigManager` | Account authentication, connection discovery and setup, brokered tool calls, optional CLI MCP configuration. |

A normal message enters `ChatViewProvider`, receives normalized authority settings and a resolved model, is stored in its panel's conversation, and triggers a checkpoint capture. Routing then selects Mysti's coordinator, explicitly mentioned agents, collaboration, or the panel's normal backend. The backend path assembles project instructions, attached files, memory, optional retrieved history, channel context, and canvas/visual tool instructions before calling `ProviderManager.sendMessage`. Providers yield `StreamChunk` events; the host forwards text, reasoning, tools, usage, questions and terminal states to the webview and persists the resulting message anatomy.

This is also the path responsible for the project-instruction and project-memory blocks in the current conversation. `ChatViewProvider` assembles `mysti.md`, `.mysti/rules`, cross-vendor instruction files such as `CLAUDE.md`, and stored project memory, wrapping the reference content in nonce-labelled untrusted blocks before forwarding it to the backend. This test application is therefore a workspace Mysti operates on; its React architecture is separate from Mysti's extension architecture.

The 15 registered backends are Claude Code, Codex, Gemini, Cline, Copilot, Cursor, OpenClaw, OpenCode, Qwen Code, Ollama, LocalAI, Hermes, Continue, OpenRouter and Kimi Code. `ManusProvider.ts` is present but unregistered. Twelve integrations use CLI transports; Ollama, LocalAI and OpenRouter use HTTP paths. OpenClaw additionally has a gateway transport, and Hermes/Kimi use persistent ACP processes. Claude also supports a persistent process. Capability metadata distinguishes real differences in tool events, native sessions, prompt-history replay, reasoning, usage, attachments and model selection. Registration does not imply every backend has feature parity.

The selected agent and concrete backend are deliberately separate concepts. Fresh selection defaults to the `mysti` pseudo-agent, while a concrete provider fallback remains Claude Code. Explicit existing agent/provider choices are preserved. The model registry merges curated, discovered and custom models; the panel resolves models against the chosen provider and records actual model attribution. Native slash commands are curated, reported by a backend, or discovered from user/project files. Execution can pass a supported command through, expand a template into a prompt, or use a Mysti equivalent.

Mysti's coordinator is distinct from a normal CLI provider. It uses DeepMyst's gateway by default, with direct OpenRouter enabled by explicit configuration. It supports model fallback, native tool calls and a nonce-tag protocol for models without native tool support. Tool results are fenced before returning to the model. Per-run counters limit model turns, delegations and tool use. Local read tools are available; writing, patching and shell execution have an additional disabled-by-default setting and workspace/mode gates. This corrects an older passage in `CLAUDE.md` that describes the coordinator as having no local write or shell tools at all. Background work uses `BackgroundJobManager`; explicit orchestration decomposes work into a validated DAG and dispatches groups through `CollaboratorPool`.

There are several collaboration systems, and they should not be conflated. The original brainstorm manager implements quick, debate, red-team, perspectives and Delphi strategies. Mentions can route tasks or select collaboration roles. The newer, currently untracked `SessionManager.ts` provides `/review`, `/panel`, `/critique`, `/race` and `/brainstorm`, with shape-specific participant minimums and all session collaborators restricted to read-only access. The common pool caps concurrent work, checks provider availability, derives child panel IDs, handles tool gates, and cancels/disposes child runs. The new session shapes include their own UI estimates and deterministic result formatting; for example, `/panel` currently renders independent answers, even though its catalog description mentions a synthesis.

Permissions combine operation mode and access level, presented as Plan, Ask, Auto and Full in the current UI. Unknown tools receive command-level classification. Workspace settings are clamped against user policy, and autonomy adds safety classification and learned preferences. Coordinator writes are directly gated before execution. CLI integrations instead often rely on streamed tool events and OS process suspension, with provider-specific native restrictions and fallbacks. `BaseCliProvider.suspendProcess` uses SIGSTOP on non-Windows platforms and reports failure on Windows. This event-driven enforcement is a sensitive architectural boundary to validate with real providers; this review does not establish that all backend events arrive before their effects. A permission card alone should not be treated as proof of a synchronous backend approval handshake.

The canvas is a document editor. Pages have `DocNode` trees with stable element IDs, typed properties, styles, text and children. Shared operations implement text/style/property updates, insertion, removal, movement and replacement. Operations carry versions and inverse changes; the executor handles stale edits, staging, rebasing and pins protecting human edits. The same operation machinery accepts human gestures and agent changes. `ArtifactStore` persists schema-versioned artifacts, operation history and content-addressed assets under `.mysti/canvas/`, using atomic writes and backups. The renderer is a separate webpack bundle with a typed protocol, incremental updates, selection/inspector/board controllers and live activity. Legacy source-based rendering remains for compatibility. Canvas tools reach agents through in-process coordinator dispatch, MCP and parsed text operations.

Visual observation is a separate feature from the canvas. `VisualSessionManager` and Playwright inspect a running local app, returning screenshots, DOM/accessibility observations, console issues and network failures. `visualTestPolicy` decides origins, paths and server startup policy. Model-driven observation and interaction have separate feature gates. Playwright is external to webpack and included as a runtime dependency in packaging; its browser executables are installed separately.

Persistence is distributed by purpose. `ConversationManager` stores bounded, schema-versioned chat data in VS Code global state. Memory lives under `~/.mysti/memory/` and project-specific `~/.mysti/projects/<hash>/memory/`; coordinator memory also uses workspace state. Compaction history is written to `.mysti/compaction/<panel>/history.jsonl`. Checkpoints use a private Git directory under extension global storage with the workspace as work tree, separate from the project's `.git`. Checkpoints are enabled by default, capped by configured file/snapshot limits, and support rewind. Agent definitions load metadata first, instructions on selection, and full content on demand from bundled, plugin, user and workspace sources. Core content is checked against a generated integrity manifest; other definitions are treated as reference data. Executable capability publication, verification and quarantine add another layer.

Token accounting has recently been centralized in `TokenAccounting.ts`. It normalizes differing provider cache conventions, distinguishes missing measurements from zero, separates current context occupancy from cumulative spend, and feeds compaction/UI calculations. `PromptCache` marks eligible stable prefixes; `SmartCompactor` considers context pressure, cache warmth and estimated economics; retrieval can bring relevant old context back. Boost applies a settings overlay and records measurements without raising permission authority.

DeepMyst keeps third-party service credentials remotely. Mysti stores its DeepMyst key in VS Code SecretStorage and presents connection flows in the webview. The connection marker protocol explains the one-click linking messages shown in chat. Enabling “Use in local CLIs” also writes a bearer-bearing broker entry into supported CLI MCP configuration files; SecretStorage is therefore not the sole location of that key when this feature is enabled. This is a behavior description, not a live credential inspection.

Desk needs careful qualification. Identity, peer book, safety-number pairing, grants and revocation are wired into activation and the chat UI. There is extensive additional implementation for signed envelopes, scopes, egress scanning, transport, dispatch, serving, proposals and audit records. However, the client, HTTP server, dispatcher and serving modules are not reachable through literal imports from either webpack entry in the current tree, and the native Desk tool vocabulary currently limits sendable verbs to status and locate. Pairing is integrated; complete cross-machine task execution should not be described as an active end-to-end feature based on these files alone.

The largest maintenance concern is concentration of responsibilities: `ChatViewProvider.ts` is 14,453 lines and `media/chat/chat.js` is 14,889 lines. They connect many asynchronous state machines, making routing, cancellation, panel isolation and UI synchronization especially important change boundaries. The current branch has 70 modified tracked files plus 16 untracked files. New session, token and CLI compatibility code is part of this working tree, not part of HEAD. Documentation contains older provider counts, test counts and subsystem descriptions, so source and call-site wiring are more reliable than the plan index for present behavior.
